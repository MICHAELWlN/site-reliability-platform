# Ansible Demo: Idempotent Nginx Configuration

A minimal configuration-management demonstration. An Ansible playbook installs and configures
Nginx on an isolated, throwaway Ubuntu container and is run twice to show idempotency.

It manages **only the test container**. It does **not** manage, connect to, or configure the EC2 instance
or any AWS resource, and it does not touch `deploy/nginx.conf`, `deploy/sre-service.service`, the Dockerfile,
the Jenkinsfile, Terraform, or the FastAPI code.

## What it does

| File | Purpose |
| --- | --- |
| `inventory.ini` | One host in group `web`, `sre-ansible-target`, reached with the `community.docker.docker` connection (`docker exec`), with `ansible_python_interpreter=/usr/bin/python3` |
| `playbook.yml` | Installs Nginx, deploys a validated config, makes sure the service is running |
| `templates/nginx.conf.j2` | Minimal config: every request returns HTTP 200 and a short text body |

The playbook uses only native `ansible.builtin` modules (`apt`, `template`, `service`). No `shell` or
`command` tasks. The config task uses `validate: nginx -t -c %s`, so an invalid config is never installed.
A handler reloads Nginx only when the config file actually changes.

## Test environment and security

- **Controller:** Ansible installed on the host (core 2.21.5 from the Homebrew `ansible` 14.5.0 package, with `community.docker` 5.4.0).
- **Target:** a plain `ubuntu:24.04` container named `sre-ansible-target`.
- The container is **not privileged**, has **no volume mounts**, and the host Docker socket is **not** mounted anywhere.
- The only published port is `127.0.0.1:18080 -> 80`, bound to loopback.
- No SSH keys, passwords, or AWS credentials are used or stored.

## Commands and actual results

Run from the repository root. Add Docker to `PATH` if `docker` is not found:

```bash
export PATH="/Applications/Docker.app/Contents/Resources/bin:$PATH"
```

**1. Syntax check** (no connection made): passed.

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml --syntax-check
# playbook: ansible/playbook.yml
```

**2. Start the isolated target.** Ansible needs Python on the target, so `python3` and `python3-apt` are
installed as the only pre-step. Nginx is left for Ansible to install.

```bash
docker run -d --name sre-ansible-target -p 127.0.0.1:18080:80 ubuntu:24.04 sleep infinity
docker exec sre-ansible-target sh -c 'apt-get update -qq && apt-get install -y -qq --no-install-recommends python3 python3-apt'
```

Checked afterwards: `privileged=false`, 0 mounts, port `80/tcp -> 127.0.0.1:18080`, Nginx not installed.

**3. First run:** installs and configures Nginx.

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml
```

```text
TASK [Install Nginx]              changed
TASK [Deploy Nginx configuration] changed
TASK [Ensure Nginx is running]    changed
RUNNING HANDLER [Reload nginx]    changed
sre-ansible-target : ok=5  changed=4  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0
```

**4. Verify HTTP:**

```bash
curl -i http://127.0.0.1:18080/
```

```text
HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Content-Type: text/plain
SRE Platform Ansible demo
```

Inside the container: package `nginx 1.24.0-2ubuntu7.18` installed, `service nginx status` reports running,
and `nginx -t` reports the configuration test is successful.

**5. Second run:** same command, no changes.

```text
TASK [Install Nginx]              ok
TASK [Deploy Nginx configuration] ok
TASK [Ensure Nginx is running]    ok
sre-ansible-target : ok=4  changed=0  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0
```

`changed=0`, and the reload handler did not run. `curl` still returned HTTP 200 afterwards.

## Cleanup

```bash
docker rm -f sre-ansible-target     # removes the container and everything Ansible installed in it
docker rmi ubuntu:24.04             # optional: remove the base image
```

Nothing else was created. No repository files are generated by running the playbook.

## Limitations

- **Container, not EC2.** This proves the playbook is correct and idempotent on an Ubuntu userland. It has not been run against the real EC2 instance.
- **No init system in the target.** A container has no systemd, so Ansible's `service` module used the SysV `service` command. Boot-time enablement (`enabled: true`) is therefore not configured or tested here. A real EC2 playbook would manage systemd units and enablement.
- **Not the production config.** The demo config returns a fixed text response. It does not proxy to the FastAPI service and is not `deploy/nginx.conf`. Pointing Ansible at the real Nginx and systemd configuration is a separate step.
- **Manual Python pre-step.** `python3` and `python3-apt` are installed on the target outside Ansible.
- **Local connection only.** The `docker` connection plugin works only on this machine. SSH inventory, secrets handling (for example Ansible Vault), and roles are out of scope.
- **Host-installed Ansible.** Results depend on the host's Ansible version. The playbook is not yet run in CI or Jenkins.
- **Single host.** The inventory has one test container. Drift correction (changing the config by hand, then re-running) was not demonstrated.
